# 2026-08-17 — Preview becomes edit-and-replace; images can be swapped without Excel

Preview stopped being read-only. Uploading a filled sheet now opens it in the same screen you'd
land on straight out of Generate — every attribute, name, tag and the HSN box editable, plus a new
way to replace a rejected product photo without ever reopening Excel or re-exporting from Shopify.

Spec: [`docs/superpowers/specs/2026-08-17-preview-edit-and-image-replacement-design.md`](../superpowers/specs/2026-08-17-preview-edit-and-image-replacement-design.md).
Plan: [`docs/superpowers/plans/2026-08-17-preview-edit-and-image-replacement.md`](../superpowers/plans/2026-08-17-preview-edit-and-image-replacement.md).
Branch `feat/preview-edit-image-replace`, 10 code tasks + this docs task, built via subagent-driven
development with a per-task review gate.

## What shipped

**Preview adopts instead of just reading.** `POST /preview` used to render read-only listing cards.
It now registers the uploaded workbook as a job in the same store a *build* uses
(`store.finish(job.id, {"filled": xlsx, "origin": "upload", ...})`) and redirects straight into the
Fill-attributes screen. Every existing surface on that screen — dropdowns, live preview card,
per-SKU save, the HSN gap banner, registry pinning — works on it unmodified, because nothing
downstream of the job store cares whether the workbook was built here or uploaded. `result["origin"]`
is the one place the two are told apart, and it exists only to drive a little UI chrome (the Clear
button, the "you have unsaved edits" confirm). A file with no product rows is refused before a job
is even created.

**Clear, with a guard once anything is saved.** Before a save, Clear is instant. After one, it asks
to confirm first — because at that point the edit lives only on the server's copy of the file, not
on the copy sitting on the owner's computer. Nothing here survives an app restart either way; the
job store has always been in-memory only (`src/web/jobs.py`), and this branch didn't change that —
it just made it matter more, since there's now real work an owner can lose by not downloading first.

**Image replacement, one slot at a time.** Each product panel gained a file picker for each of the
seven image columns (`IMAGE_COLUMNS` in `src/myntra/fill.py`: Front, Side, Back, Detail Angle, Look
Shot, and two Additional slots). Pick replacement photos, save, and each one is independently
validated against `config/myntra/image_specs.yaml` (≥700×700, ≤10MB), converted to JPEG, and hosted
on S3; the resulting URL is written into the sheet through the same `write_attributes` path an
attribute save uses (write-lock, SKU verification, shared-string re-apply — nothing new invented for
images). **Per-slot failure isolation** was a deliberate design point, not an accident of the code:
`image_replace.prepare()` never raises. A corrupt file, an over-large photo, or an unsafe SKU comes
back as a reason string scoped to *that slot only*. Submit seven photos where one is bad, and the
other six still land — you don't lose a batch to one mistake.

**The Fix-flow entry point.** A fix result that still has photo-category `manual_needed` issues now
shows a "Replace images for N SKU(s)" button. It opens the corrected sheet directly in the editable
screen via a new route, `POST /preview/adopt-fix/{fix_id}`, which does the same job-adoption thing
`POST /preview` does, just seeded from `myntra_corrected.xlsx` instead of an upload. This works for
all three fix input formats the app accepts (per-SKU xlsx, file-level csv, MDirect Listings Report)
because it hangs off the fix *result*, not off how the rejection file was read.

## The content-addressed key, and why it has to be that way

The build path writes an image as `{sku}/{n}.jpg`. A replacement is written as
`{sku}/{slot}-{hash}.jpg` instead, where the hash is the SHA-256 of the uploaded file's own bytes
(`image_replace.replacement_key`).

This isn't decoration — it's the mechanism that makes replacement work at all. Myntra, and any CDN
or browser cache sitting in front of the bucket, cache by **URL**. If a corrected photo were written
to the *same* URL as the one Myntra just rejected, a cached copy of the old image could keep being
served with nothing to force a re-fetch — the correction would silently not take, and there is no
reliable way to make Myntra re-pull an unchanged URL on demand. Deriving the filename from the
image's own content sidesteps the problem: a genuinely different photo always gets a different URL,
so it's always fetched fresh, while re-uploading the identical file twice is idempotent (same bytes
→ same hash → same key, no duplicate object piling up in the bucket).

The `sku` half of that key comes straight off a form field, so it's user input landing in a
filesystem path and an S3 key. It's validated against `[A-Za-z0-9_-]{1,64}` — no dots, deliberately;
a charset that allowed `.` would let a literal `..` traverse one directory level. This isn't
theoretical caution: an automated commit review during the build (Task 6) caught the SKU going into
`prepare()`'s path/key with **no sanitization at all** as a real HIGH-severity path-traversal finding
— the fix added the guard, and a follow-up review round specifically rejected a looser charset
(`[A-Za-z0-9._-]`) that a reviewer had first suggested, because a literal `..` still matches it.

## SKU editing: left out on purpose

The SKU is not editable anywhere in this screen. It's the product's identity across three separate
columns Myntra reads — `vendorSkuCode`, `SKUCode`, `vendorArticleNumber` — and Myntra keys on it. The
spec considered and explicitly declined to solve Myntra's "style already present" rejection (the
owner's report is that Myntra support's own advice is "change the SKU a little," and whether a
rejected style leaves a live listing behind is unclear even to them). Rather than build a half
answer to a question nobody's sure of the mechanics of, this branch ships image replacement — which
*is* well understood — and leaves the SKU lever where it already was: in the owner's hands, in
Excel, with one sharp edge written down verbatim on the Preview screen:

> If you change a SKU by hand in Excel, change it in **all three** columns —
> `vendorSkuCode`, `SKUCode` and `vendorArticleNumber` — or Myntra receives an
> inconsistent identity for that product.

## Two things worth flagging honestly

**The S3 leg of image replacement has not been exercised against real AWS credentials.** Every test
for `image_replace.host()` runs against an injected/fake boto3 client — that's real coverage of the
upload *logic*, but it has never actually round-tripped a file to the `ijorethnicpartners` bucket
and back. The public-URL shape, region, and bucket policy are the same ones the build path already
uses in production, so the risk is contained, but "contained" isn't "verified."

**Nothing on this branch has been run by the owner in the real app yet.** All ten code tasks passed
their scoped test runs and a per-task automated review (several went through one fix round each,
including a real path-traversal finding on the image-key sanitizer and a real "exception becomes a
swallowed 500" finding on the image-save route, both fixed before the task was called done — the
session's build ledger, kept locally under `.superpowers/sdd/` and not part of the repo, has the
full detail). None of that substitutes for Gopal clicking through it. The manual check called for in
the plan — upload a filled sheet, change an attribute, replace an image, download, open in Excel,
confirm the value changed and the image URL carries a hash suffix and the dropdowns still work —
has not been run as of this entry.

## Process note

Two build constraints turned out to matter across nearly every task on this branch and are worth
recording once, here, rather than per-task: the Bash tool's 600-second ceiling means
`tests/web/test_attributes.py` (61 tests, ~40 minutes) can never run whole inside one call — every
task from here needs a narrowed `-k` selection, split into multiple foreground batches if the
narrowed set still runs long. And background-by-default test runs stall silently more than once
during this branch; naming one test file and passing `run_in_background: false` explicitly, every
time, is what avoided it.

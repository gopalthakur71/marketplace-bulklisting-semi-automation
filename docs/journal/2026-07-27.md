## The feature being specced

Filling the seller-decided attributes means downloading the sheet, hunting through a ~200-column
spreadsheet, and typing into Excel — with the product photo nowhere in sight. The approved design moves
that into the app: after a build, an optional **"Fill attributes"** screen shows one accordion panel per
SKU with the product photo, 12 dropdowns whose options come **strictly** from the Myntra template
vocabulary, and a **live listing preview** that re-renders server-side on every change by calling the
existing `src/myntra/preview.py` reconstruction. One Save writes every SKU into the already-built
workbook. The Excel path and the `/preview` round-trip both stay exactly as they are — this is purely
additive, and skipping the screen leaves the file exactly as it is today.

Also widens the user-filled set from 9 to **12**: `Second Prominent Colour`, `Third Prominent Colour`
and `Usage` join the list. All three verified live against the V13 template (53 / 53 / 9 values).

## The finding worth remembering

Writing the spec against the real code turned up a constraint the brainstorm had missed.

`src/myntra/fill.py` does not stop at `wb.save()`. It then rewrites the `Sarees` sheet XML converting
**shared strings to inline strings**, because Myntra's upload parser does not resolve shared strings.
The approved design said "Save writes into the already-built xlsx via openpyxl" — and a plain openpyxl
save **re-introduces shared strings**, silently undoing that. The file would look perfect in Excel and
be rejected by Myntra, with nothing in the app to hint why.

So the save path must re-apply the conversion (spec §6.2, plan Task 3), and there is now a test that
asserts no `t="s"` cells survive an in-app save. This is also written into `AGENTS.md` as an invariant,
because the next person to re-save a built workbook will hit it too.

The other invariant the plan pins down with a test: **the downloaded file must still have live Excel
dropdowns** after an in-app save. That is the whole reason the pipeline moved to the V13 template, and
it is the check the owner does first.

# Same day, later — the plan got built (Flow D is live in code)

The design day above turned into a build day. All 7 plan tasks are implemented on the same
branch.

## What shipped

`GET /generate/attributes/{job_id}`, reachable from a new **✎ Fill attributes** button on a
finished Generate result:

- one `<details>` accordion panel per SKU — product photo (from the job's Shopify export, joined
  by SKU), the 12 dropdowns, and a listing preview card;
- dropdown options read **live from the V13 template's `vocab_by_header`** — nothing invented,
  `NA` offered only where Myntra's own sheet lists it;
- the preview re-renders server-side on every dropdown change (`POST .../preview`, htmx),
  calling the **existing** `src/myntra/preview.py` reconstruction rather than duplicating the
  wording rules in JS;
- one **Save** (`POST .../{job_id}`) validates every value against the vocabulary, then writes
  all SKUs into the workbook the app already built. An off-vocab value aborts the entire save
  and writes nothing, returning a 200 htmx panel (never a swallowed 500).

Filling is optional and resumable: skipped columns stay blank and keep their Excel dropdown,
saved ones come back pre-selected with an `n/12 filled` counter per panel.

Along the way: `preview.build_card` + `_preview_card.html` were extracted so Flow C and Flow D
render the identical card from identical data, and `src/web/routers/preview.py` lost its private
copy of the column-list loader — `attribute_entry.user_filled_attributes` is now the only one.

## The shared-string finding, confirmed in practice

The constraint the spec predicted (§6.2 above) was real. `write_attributes` now re-applies
`fill.shared_to_inline` after its openpyxl save, and `test_write_attributes_keeps_strings_inline`
asserts no `t="s"` cell survives. Dropdown survival is locked twice — at unit level
(`test_write_attributes_preserves_dropdowns`) and end-to-end through the Save route
(`test_save_keeps_dropdowns_alive_in_the_downloaded_file`).

## A Jinja trap that cost a debug cycle

The panel dict originally carried the chosen values under the key `values`. In a Jinja template,
`p.values` resolves to **`dict.values` — the built-in method** — not the key, so the
pre-selection comparison was silently always false, while the `n/12 filled` counter (key
`filled`, no collision) rendered correctly and made the page look right. The key is now `chosen`,
with a comment saying why. Worth remembering: any dict passed to Jinja must avoid `values`,
`items`, `keys`, `get`, `update`, `copy` as key names.

## Follow-up the same day: Brand Colour (Remarks) fills itself

Gopal asked for brand colour on the attribute screen "as well". Digging in turned up that
`Brand Colour (Remarks)` is **mandatory, free-text, and filled by nothing** — it is absent from
`column_map.yaml`, `constants.yaml` and `user_filled_attributes`, so every generated sheet left
it null, Myntra rejected the rows with `Brand Colour (Remarks) cannot be null`, and Flow B
recovered by asking for a Prominent Colour and mirroring it in lowercased
(`corrector.py:88-90`). A rejection round-trip for a value we could already derive.

His call: **it follows Prominent Colour and the app fills it automatically** — no dropdown, no
text box. `attribute_entry.derive_brand_colour` does the derivation, the save route folds it in
before `write_attributes`, and the panel shows the result read-only ("filled automatically from
Prominent Colour") so it is automatic without being silent.

The one sharp edge: `NA` is a *real member* of the Prominent Colour vocabulary, so a plain
truthiness check would have written the literal string `"na"` into the sheet. `preview.is_set` is
the shared guard; blank and `NA` both mirror to nothing. Spec:
`docs/superpowers/specs/2026-07-27-brand-colour-auto-fill-design.md`.

Note this only fixes sheets saved through Flow D. A seller who fills the attributes in Excel
still gets a blank Brand Colour and still needs Flow B — worth revisiting if that path stays in
regular use.

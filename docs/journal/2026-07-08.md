## The prod bug — Surface-B Proceed was a silent 500 (`161c69c`)

Found on a live re-verify the morning after the big deploy. The Fix flow's **Proceed** button did
nothing for Listings-Report and file-level-CSV rejections. Root cause, three layers deep:

1. **Surface B rebuilds by re-running the pipeline**, which needs the Shopify `products_export.csv`.
2. **Prod has no baked-in export** (the `.dockerignore` correctly keeps input data out of the image), so
   `pipeline.main` hit a missing `input/products_export.csv` → `FileNotFoundError` → **HTTP 500**.
3. **htmx only swaps on 2xx**, so the 500 was swallowed with no UI change — the button looked dead.

The fix, three parts:

- **Require + thread the export.** Surface-B rebuilds now prompt for the products export, save the
  uploaded file, and pass it through `regenerate_surface_b(..., csv_path=...)`. Missing export → a clear
  "upload your products export" panel, no rebuild.
- **Never a bare 500 again.** `/fix/apply` is wrapped so any exception renders a **200 error panel** (a
  real `HTTPException`/404 still passes through). The exception detail is **HTML-escaped** — an XSS fix
  flagged in the security review.
- **A real e2e.** The old Surface-B e2e monkeypatched `regenerate_surface_b`, so it never exercised the
  pipeline path that actually broke. Replaced with a genuine drive of `pipeline.main` from an uploaded
  export that downloads a valid xlsx — closing the coverage gap that let this ship.

**166 tests pass.** ff-merged to `main` (`161c69c`), CI/CD green, restarted on EC2 via SSM.

> **Lesson (recorded in memory as [[fix-surface-b-export-bug]]):** a monkeypatched e2e is not an e2e. The
> one path a prod deploy most needs covered — real inputs, real pipeline — is the one a stub silently
> skips.

## The two-action Fix screen (what it now does)

On the Fix review screen the rejected SKUs split into two groups; **both** now end in a downloadable
Myntra sheet, behind the same Proceed / Do-not-change gate:

- **"We can fix these"** (correctable / instant-text — address, pincode, MRP/ISP) → **"Download now to
  fix"** rebuilds just those SKUs with the fix applied. Button moved out from the bottom of the form (it
  was off-screen below the explain-only group) to right under its own cards. (`359aaa3`)
- **"You must fix these yourself first"** (explain-only — photos, quality, resolution) → new **"Download
  listing file for these SKUs"** button + guidance describing the real workflow: reshoot in Shopify →
  re-export just those SKUs → drop the file in → the app rebuilds a Myntra sheet for **only** them,
  pinning the **same HSN + styleGroupId as the first attempt** (from the SKU registry) so Myntra won't
  re-reject on identity drift. (`76790a0`, `e94a26f`)

Both buttons submit the same form; the clicked button's own `name="action"` value (`fix` | `manual`)
tells the server which SKU set to rebuild. One **shared Shopify-export upload**, lifted to the top of the
form so it's visible whichever button is clicked. This flow lives on the **Fix** page — not Generate —
precisely because Generate would trip the pre-upload duplicate-SKU guard on these already-registered SKUs.

Built TDD, failing tests first; a **real-pipeline manual-rebuild e2e** (`de874a2`) guards the same
coverage gap that bit the Surface-B bug. **171 tests pass.** ff-merged to `main` (`359aaa3`) + pushed.
